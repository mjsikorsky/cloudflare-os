# External native contributions

An authenticated build-capable `Overseer` can mint `createContribution(chatId, {id, name})` for an existing native chat. The resulting `WorkspaceContribution` binds one native workspace, one chat and an explicit `agent` author. It reuses native source snapshots, provisional gadget creation, chat drafts and draft finalization. The holder cannot accept/revert changes, write committed mainline, approve actions, obtain connected-account or gadget runtime capabilities, or select another destination.

Minting follows the ordinary `openGadget` sharing and observer checks. A use-only viewer cannot mint. Parent disposal, native sharing revocation/Overseer restart, workspace deletion or chat deletion ends access. Operations refuse while the native chat has an active agent rather than overriding native draft conflict rules. Finalization produces proposed changes; acceptance remains an independently authorized native operation. A caller should retain the parent while delegation is intended and dispose both when finished. Reconnect through fresh native admission and mint a new contribution for the existing chat; no parallel proposal store is necessary.

The agent descriptor is attribution supplied by the delegating user; it is not a user identity, billing grant or permission. Observation returns only source bytes and workpiece metadata visible to the bound chat. It does not execute gadgets or return capability-bearing account/runtime objects. The contribution's required explicit gadget binding name avoids invoking a model simply to select a name.

## Ownership integration still required

One host person must retain one native identity across organizations and selected workspaces. That is independent from resource ownership. Current native workspace ownership is personal: User DO registration supplies `ownerId`; its listings, models, connections and blueprint author/accounting relationships all rely on that person.

Organization/workspace-owned resources require an explicit native owner reference and native owner discovery, with camelAI retaining live membership and billing authority. Both `newGadget` and `newGadgetFromBlueprint`, plus external-message workspace initialization, must use that ownership rule. Child workpieces and published blueprints inherit resource ownership while preserving human/agent authorship separately. A group must not masquerade as a User DO. Native access minting must join resource-specific host membership with native sharing/observer checks, and membership revocation must invalidate retained capabilities, using the native revocation/reopen mechanism. The contribution interface does not implement these ownership requirements or claim them complete.

## Focused native qualification

Run `node --test __integration__/workspace-contribution.test.mjs` from `packages/workshop-backend`. The test builds only this backend with its normal Wrangler dry-run and validation pipeline, then uses an external Node Cap’n Web client against the real native worker, User/Overseer SQLite state, sharing and draft lifecycle in isolated Miniflare. Build output is retained in a fresh temporary directory for diagnosis. No provider or gatekeeper operation is exercised. Keeping the client outside workerd avoids a same-workerd client test-runtime defect where caught RPC rejections are independently reported as unhandled; the test suppresses no errors.

External agents can import `applyWorkspaceFileEdit` and `WorkspaceFileEdit` from `@gadgets/workshop-shared/workspace-code`. This is the same pure helper used by the native agent for file writes and exact-match edits. Decode the authorized observation into a Y.Doc, resolve the selected workpiece’s `filesRoot` from native metadata, capture its state vector, apply the edit, then submit the encoded V2 delta through `proposeCode`. Resolve the root in trusted consumer code; do not make arbitrary root names a model-facing argument. The helper grants no authority and does not replace native read-before-edit, proposal or acceptance policy.
